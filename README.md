# AI-помощник для карточек товаров КИП

Прототип сервиса, который по данным о контрольно-измерительном приборе готовит черновик карточки товара для B2B-интернет-магазина:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1200 символов;
- таблица ключевых характеристик;
- 3–5 поисковых запросов;
- commercial-блок для менеджера: кому подходит прибор, какие задачи решает, как его предложить.

Данные вводятся через веб-форму или JSON-файлом, результат отдаётся как карточка, обычный текст, Markdown или JSON — с кнопками копирования и скачивания. Модель локальная (Qwen3.5-4B в vLLM): ключи API не нужны, данные никуда не уходят.

Главное ограничение задачи — модель не должна выдумывать характеристики. Поэтому таблицу характеристик собирает код, а не модель, а тексты модели проходят автоматическую проверку фактов (подробнее — в разделе [Как защищаемся от выдуманных характеристик](#как-защищаемся-от-выдуманных-характеристик)).

## Быстрый старт

### Что нужно

- видеокарта NVIDIA с 8 ГБ памяти или больше;
- Docker с поддержкой GPU и Docker Compose v2.30+:
  - Windows — Docker Desktop с бэкендом WSL2 и свежим драйвером NVIDIA;
  - Linux — Docker Engine и [NVIDIA Container Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html);
- около 10 ГБ на диске под образ vLLM и веса модели.

### Запуск

```bash
git clone <ссылка на репозиторий>
cd <папка репозитория>
docker compose up -d --build
```

Первый запуск скачивает веса модели (~5,5 ГБ) и занимает 5–15 минут, дальше модель загружается за 2–3 минуты. Готовность видно по статусу `healthy`:

```bash
docker compose ps
```

Интерфейс открывается на <http://localhost>. Пока модель загружается, вместо формы показывается сообщение о её недоступности и кнопка «Проверить снова».

Остановить: `docker compose down`. Скачанные веса остаются в Docker-томе `hf-cache` и при следующем запуске не скачиваются.

### Настройки и секреты

| Файл | В git | Что внутри |
| --- | --- | --- |
| [.env.public](.env.public) | да | все настройки с комментариями: модель, параметры vLLM, температура, таймауты |
| `.env` | нет | секреты: `HF_TOKEN`, ключ облачной LLM. Шаблон — [.env.example](.env.example) |

Для запуска `.env` не нужен. Значения из `.env` перекрывают `.env.public`, переменные окружения перекрывают оба файла.

## Как пользоваться

### Веб-интерфейс

1. Заполните форму одним из способов:
   - вкладка **«Шаблон»** — выберите тип прибора, и в таблицу характеристик подставятся обязательные для него поля;
   - вкладка **«JSON»** — загрузите файл в формате ниже, например из папки [examples](examples/);
   - или просто введите данные вручную.
2. Нажмите **«Сгенерировать»**. Пока не заполнены название и обязательные для категории характеристики, кнопка неактивна, а под ней написано, чего не хватает.
3. Результат открывается на вкладках **«Карточка»**, **«Текст»**, **«Markdown»** и **«JSON»**. На каждой — кнопка «Скачать» и кнопка копирования в углу блока.

Если автоматическая проверка нашла в текстах проблемы, которые модель не исправила, они показываются над карточкой — их стоит просмотреть перед публикацией.

### Формат входного JSON

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5",
    "присоединение": "G1/2",
    "диаметр корпуса": "100 мм"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Обязательно только `name`. Пустые `manufacturer`, `description` и характеристики допустимы — в карточке они попадают в раздел «Требует уточнения». Неизвестные поля не мешают генерации: они игнорируются и перечисляются в поле `ignored_fields` JSON-результата. Один файл — один товар.

### Пакетная генерация из консоли

Для запуска вне Docker нужен [uv](https://docs.astral.sh/uv/). Модель при этом работает в контейнере vLLM, порт 8000 открыт:

```bash
uv sync
uv run python app/cli.py examples/*.json --out examples/output
```

Для каждого файла сохраняются `.md` и `.json`. Код возврата: 0 — все карточки готовы, 1 — часть файлов с ошибками, 2 — LLM недоступна.

## Примеры результата

| Вход | Результат |
| --- | --- |
| [manometer_dm02.json](examples/manometer_dm02.json) | [Markdown](examples/output/manometer_dm02.md), [JSON](examples/output/manometer_dm02.json) |
| [pressure_sensor.json](examples/pressure_sensor.json) | [Markdown](examples/output/pressure_sensor.md), [JSON](examples/output/pressure_sensor.json) |
| [incomplete_thermometer.json](examples/incomplete_thermometer.json) | пример некорректного входа: генерация отклоняется с понятным сообщением |

В PDF с заданием приведён только один товар — манометр DM 02, он взят как есть. Данные датчика давления составлены для примера: производитель указан как «Тестовый производитель».

Обратите внимание на манометр: во входе нет измеряемой среды и температуры рабочей среды, которые для манометров обычно указывают. В таблице они стоят со значением «данных нет», попадают в «Требует уточнения», а модель получила указание о них не писать.

## Как это работает

```text
JSON / форма
  → разбор и нормализация входа (pydantic)
  → категория прибора по названию и проверка обязательных характеристик
  → запрос к LLM с ответом строго по JSON-схеме
  → автоматическая проверка ответа
      → есть замечания: повторный запрос с конкретным списком проблем (до 3 попыток)
  → карточка: тексты модели + таблица характеристик, собранная кодом
```

### Как защищаемся от выдуманных характеристик

Промпт запрещает додумывать, но маленькая модель всё равно ошибается, поэтому защита в основном в коде:

1. **Таблицу характеристик модель не пишет.** Её собирает код из входных данных, поэтому выдуманное значение в таблице появиться не может.
2. **Недостающие характеристики помечаются «данных нет».** Для каждой категории прибора известен список ожидаемых характеристик. Те, что отсутствуют во входе, попадают в таблицу с пометкой «данных нет», а модель получает их список с указанием не упоминать.
3. **Каждое число в текстах сверяется со входом.** Если в заголовке, описании, запросах или commercial-блоке есть число, которого нет во входных данных, это замечание. В нём указан и контекст: модели проще исправить «6 в "манометр 1 6 мпа"», чем просто «6».
4. **Рискованные сведения проверяются по списку.** ГОСТ, ТУ, степень защиты IP, взрывозащита, поверка, Госреестр, сертификация, гарантия, цифровые интерфейсы, материалы — всё это допустимо, только если есть во входе.
5. **Найденные проблемы уходят модели на исправление.** Она получает свой прошлый ответ и конкретные замечания. Из всех попыток выбирается ответ с наименьшим числом замечаний, а оставшиеся замечания показываются контент-менеджеру.
6. **Правки кода не добавляют фактов.** Например, если описание вышло длиннее 1200 символов, код убирает последние предложения, а не просит модель переписать текст.

### Промпты

Тексты промптов лежат отдельными файлами в [resources/prompts/](resources/prompts/) — их можно править без изменения кода. Ограничения (70 символов, 800–1200, 3–5 запросов) подставляются из тех же констант, которыми код проверяет ответ, поэтому промпт и проверка не расходятся.

- **[system.txt](resources/prompts/system.txt)** — роль (технический копирайтер B2B-магазина КИП), главное правило «ничего не выдумывать» с перечнем того, что модели склонны додумывать, требования к каждому полю ответа и стиль.
- **[user.txt](resources/prompts/user.txt)** — данные о товаре, автоматически определённая категория и список характеристик, которых нет во входе и о которых нельзя писать.
- **[fix.txt](resources/prompts/fix.txt)** — повторный запрос: список найденных проблем и просьба исправить только их, не добавляя новых фактов.

Решения в промптах:

- **Промпты на русском.** Результат нужен на русском, и с русским промптом модель меньше смешивает языки и точнее держит терминологию.
- **Данные отделены тегом `<данные>`** с явным указанием, что это сведения о товаре, а не инструкции. Так текст описания из паспорта не может перехватить управление моделью.
- **Длина описания задана структурой, а не символами.** Модели плохо считают символы, но хорошо держат «4 абзаца по 2–3 предложения». В замечаниях о длине тоже говорится, сколько предложений добавить или убрать.
- **Формат ответа задаёт JSON-схема.** vLLM ограничивает генерацию схемой (structured outputs), поэтому невалидный JSON или лишние поля модель вернуть не может.

### Шаблоны категорий

Всё, что сервис знает о типах приборов, лежит в JSON-файлах в [resources/templates/](resources/templates/): манометр, датчик давления, термометр, расходомер, уровнемер и «другой прибор». Каждый шаблон задаёт ключевые слова для распознавания категории по названию, обязательные характеристики (без них генерация не запускается) и рекомендуемые (без них — «данных нет»). У характеристики есть варианты названий: например, «основная приведённая погрешность» засчитывается как класс точности. Новый тип прибора добавляется одним JSON-файлом, без изменения кода.

### Обработка ошибок

| Ситуация | Что происходит |
| --- | --- |
| Некорректный JSON, список вместо объекта, неверные типы полей | понятное сообщение с указанием места ошибки, генерация не запускается |
| Нет названия или обязательных для категории характеристик | кнопка генерации неактивна, под ней перечислено, чего не хватает |
| Пустые необязательные поля | генерация идёт, поля попадают в «Требует уточнения» |
| Неизвестные поля во входе | игнорируются и перечисляются в `ignored_fields` JSON-результата |
| Модель не загружена, сервер недоступен | вместо формы — причина и кнопка «Проверить снова» |
| Таймаут, обрыв связи, ошибка HTTP | сообщение с подсказкой, что проверить; сбои связи и ответы 429/5xx повторяются автоматически |
| Модель вернула невалидный или обрезанный ответ | повторный запрос с другим seed, в пределах лимита попыток |

## Принятые решения

- **Локальная модель вместо облачного API.** Ключ не нужен, данные не покидают машину, нет оплаты за токены. Цена — нужна видеокарта.
- **vLLM + Qwen3.5-4B (W4A16).** Квантованная 4B-модель помещается в 8 ГБ видеопамяти. vLLM даёт OpenAI-совместимый API и structured outputs по JSON-схеме. Режим рассуждений Qwen отключён: для копирайтинга он не нужен, а ответ без него быстрее.
- **Клиент — официальный OpenAI SDK.** Он работает с любым OpenAI-совместимым сервером, а адрес и модель задаются в `.env`.
- **Streamlit** — простая веб-форма без отдельного фронтенда.
- **Вся работа в Docker Compose:** проект запускается одной командой, код и ресурсы монтируются в контейнер, правки видны без пересборки.

## Ограничения

- **Качественные утверждения проверка не ловит.** Числа и термины из списка сверяются надёжно, но фразы вроде «обеспечивает высокую степень надёжности показаний» или перечень отраслей применения модель формулирует сама. В примере манометра такие фразы есть. Это смысловые обобщения, а не выдуманные характеристики, но перед публикацией их стоит прочитать.
- **Небольшая модель.** 4B-модели иногда пишут неестественно (например, «г1/2» вместо «G1/2» в поисковом запросе), а результат меняется от запуска к запуску.
- **Нужна видеокарта NVIDIA.** Без неё можно подключить другой OpenAI-совместимый сервер через `LLM_BASE_URL` (запуск вне Docker), но проверено только с vLLM. В запросе передаётся параметр `chat_template_kwargs`, специфичный для Qwen: облачный API OpenAI его не примет.
- **Состав категорий — экспертное допущение.** Обязательные и рекомендуемые характеристики в шаблонах стоит согласовать с контент-менеджером.
- **Один товар за раз.** JSON-файл содержит один товар, список товаров не принимается. Несколько файлов разом обрабатывает только консольный режим.
- **`null` в характеристике считается ошибкой входа**, а не пустым значением: пустую характеристику нужно передавать пустой строкой.

## Возможные улучшения

- **Проверка фактов вторым вызовом LLM.** Отдельный запрос, который сверяет каждое утверждение текста со входными данными, поймал бы выдуманные свойства, которые не видит проверка по числам и терминам.
- **Модель покрупнее** (Qwen3.5-9B на 12+ ГБ, задаётся одной строкой в `.env.public`) или облачная LLM для более живого текста.
- **Few-shot примеры** хороших карточек в промпте для каждой категории.
- **Набор эталонных товаров и метрики** (доля карточек без замечаний, число попыток) для оценки изменений промптов.
- **Редактирование шаблонов категорий и промптов в интерфейсе** — файлы уже вынесены в `resources/`.
- **Пакетная загрузка и выгрузка в интерфейсе.**

## Структура проекта

```text
app/                    код (корень исходников: импорты вида from core.models import ...)
  ui.py                 веб-интерфейс (Streamlit)
  cli.py                пакетная генерация из консоли
  core/
    pipeline.py         сборка карточки: вход → LLM → проверка → исправления
    llm.py              клиент OpenAI-совместимого API, обработка ошибок
    checks.py           проверка ответа: длины, числа, рискованные термины
    validation.py       разбор и нормализация входа
    templates.py        категории приборов и ожидаемые характеристики
    prompts.py          сборка сообщений из файлов промптов
    postprocess.py      безопасные правки ответа (обрезка лишних предложений)
    render.py           карточка в текст, Markdown и JSON
    models.py           модели данных и ограничения из задания
    config.py           настройки (pydantic-settings)
resources/
  prompts/              тексты промптов
  templates/            шаблоны категорий приборов
examples/               входные примеры и результаты (output/)
tests/                  тесты (pytest), LLM подменяется заглушкой
```

## Разработка

```bash
uv sync                    # зависимости, включая инструменты разработки
uv run pytest              # тесты
uv run prek run -a         # все проверки: ruff, ty, форматирование, тесты
```

Отладка в контейнере: `docker compose -f docker-compose.yml -f docker-compose.debug.yml up -d --build app` запускает интерфейс под debugpy на порту 5678. В VS Code для подключения есть конфигурация «Отладка app в Docker».
